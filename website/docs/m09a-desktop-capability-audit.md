## Setup journey

1. **Wallet:** React form requires an address (max 106 characters); Rust validates a mainnet public receiving address, persists it in local setup, and returns a masked summary. Errors are surfaced without treating a seed phrase/private key as valid intent.
2. **Pool:** user manually enters host, port, optional worker, and TLS choice. Rust normalizes and validates typed fields; there are no suggested pools. Pool connection does not occur during setup.
3. **Power:** Quiet/Balanced/Performance map to static fractions of logical CPU threads (quarter, half, all, minimum one). It is configured thread count, not measured wattage or a CPU cap.
4. **Review:** acknowledgement is tied to setup revision and disclosure version; changed settings invalidate it. Review covers energy, variability, upstream donation, security software, inactive Ember contribution, and no auto-start.
5. **Ready:** Rust recomputes engine verification, wallet/pool/profile validity, consent and process-conflict checks. Start button consumes `startAllowed`; Ready is permission to attempt start, not evidence of a connected pool.

Persistence is local JSON under the per-user Ember data directory with atomic setup writes. Native validation and UI errors exist. Pool suggestions are placeholder/future content; profile choices are working static controls, not adaptive power management.

## Mining lifecycle

`start_mining` rechecks setup and revision-bound consent, verifies pinned installed engine, creates a private session configuration and token, spawns XMRig under the supervisor, assigns the child to a kill-on-close Windows Job Object before resume, and waits for authenticated API readiness. Readiness requires miner identity, RandomX and positive short-window hashrate; timeout/exit/cancellation becomes an error and cleans up the owned child. Session state and configuration are runtime-owned; restart does not restore an active session.

`stop_mining` closes the owned process tree immediately (zero grace period), updates lifecycle/event state and returns setup readiness. Quit/close paths are gated through cleanup. Source and deterministic tests establish implementation; owner evidence establishes Start → Mining only. Current-release Stop/Quit acceptance remains an explicit open boundary. Never run a miner simply to produce website proof without a separately authorized milestone.

## Events and history

Event categories are system, pool, result; sources are Ember lifecycle and XMRig summary. Types include session starting/started/stopped/failed, pool connection changes and accepted/rejected result deltas. Rust supervisor owns event creation; frontend translates only for presentation. Event IDs are monotonic within process, timestamps are Unix milliseconds, and ordering follows insertion. Session IDs are opaque and events are scoped to the current in-memory session buffer. No persistent mining history, cross-restart archive or lifetime totals are evidenced.

High confidence in source wiring and deterministic behavior where listed tests exist. Moderate confidence in current Windows process/provisioning integration based on implementation and recorded owner evidence. Limited confidence in complete end-to-end lifecycle because Stop/Quit owner acceptance remains open. No M09A claim is based on a miner launched during this audit.

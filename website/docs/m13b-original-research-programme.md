# M13B — Original research programme

24 November 2026. **Proposed methods, no measurements or experiments conducted.** No miner, benchmark, stress test, pool connection, privileged action or hardware change was run. Owner hardware use requires separate explicit authorization. [Evidence and candidate questions](m13b-search-intent-research.md), [tool dependencies](m13b-interactive-resource-opportunities.md), [milestone sequence](m13b-content-growth-roadmap.md).

## Start with two modest studies

**E01, thread count against sustained hashrate and wall power**, offers the strongest combination of user need, explanation and reusable data. **E02, idle versus active whole-system power**, establishes the measurement boundary needed for trustworthy costs. Run both on one owner-operated existing PC after authorization and equipment review. Treat this as a case study, not a CPU ranking, buying recommendation or representative population result. Do not purchase hardware or promise a useful result before feasibility is known.

C02 and C08–C10 show comparison/efficiency questions; they supply no validated measurements. T11 documents benchmark modes and T01/T06 provide configuration context. Prior official/competitor hardware examples remain attributed external evidence, not Ember results. Third-party benchmark redistribution is a separate rights question, not solved by this programme.

## Common protocol inherited by every experiment

| Field | Proposed requirement |
| --- | --- |
| Hardware record | Exact CPU/stepping if available, physical/logical counts, motherboard/firmware, RAM capacity/channel topology/speed/timings, PSU, cooling, storage, graphics/display and network equipment included at the wall. State socket/NUMA topology and whether meter powers only the PC. Do not infer measured AC load from TDP or package telemetry. |
| Software record | Use **XMRig 6.26.0** as an initially source-reviewed protocol pin (T15–T17), not a claim it remains latest. Verify official release provenance and suitability at experiment start; if a newer release is selected, review sources and freeze that version for the whole dataset. Record OS build, binary/build type/SHA-256, exact algorithm variant, profile/affinity, page allocation and optimization state. No mixed `rx/0`, `rx/2` or `rx/wow` comparisons. |
| Other software | Existing manufacturer-supported temperature/clock/power telemetry or a reviewed logger; document tool version, polling overhead and sensor meaning. Meter export/logger is optional; manual interval energy readings are acceptable. No new service/account or local API exposure required. |
| Meter | Appropriately rated intact plug-in **true-power/energy** meter suitable for the PC and local socket; record model, resolution, specified accuracy and sampling/integration method. No mains modification. Meter display resolution alone is not accuracy or calibration. Obtain operator authorization before load testing. |
| Workload | Fixed-work offline benchmark first for computation validity; T11 differentiates offline from submitting online. Sustained performance requires a separately approved bounded workload/mode. A repeated finite offline workload may leave initialization gaps; report that duty cycle. Actual pool mining requires explicit authorization and records of donation/failover periods, job changes and unavailable intervals. No indefinite unattended stress run. |
| Window | Proposed initial trial: at least 10 minutes warm-up, then 30 minutes measured steady activity, logging at 10-second intervals where supported. Extend warm-up if clocks/temperatures still drift; record the rule and actual durations. If only interval kWh is available, choose a longer period sufficient for meter resolution. Short fixed-work runs are reported separately. |
| Synchronization | Start/end wall energy and hashrate interval together; record monotonic elapsed time plus UTC timestamps. Preserve dataset initialization, warm-up, active and cooldown labels. Average watts = `1,000 × interval kWh / interval hours`; H/s = measured hashes / active seconds where available. Do not call average of incompatible displayed windows a matched rate. |
| Controls | Keep algorithm/version, memory layout, OS/security settings, background tasks, power plan/limits, fan policy, peripherals/display, room conditions and measurement boundaries unchanged except the named independent variable. Record ambient temperature and workload changes; no updates/reboots mid-comparison unless explicitly part of design. |
| Repetition | At least three independent launches per condition; record all runs, not just maximum. Balance/randomize condition order to reduce warm-up/time bias, with cooldown back to a recorded baseline. Repeat at least one baseline at the end; for E01/E02 seek a second session/day. Repeated time samples within a run are not independent trials. |
| Analysis | Report each run, median and range across runs; label n as runs **and** machines. Ratio uses matched run H/s and average total wall watts, not unmatched maxima/minima. Use total hashes/total joules for pooled interval efficiency if available. Never infer a population confidence interval from n=1 PC. |
| Exclusions | Predefine invalid-computation, incomplete meter/log, external task interruption and protocol-deviation handling. Retain invalid/excluded rows with reason; do not discard a valid slow result as an outlier simply for being slow. Separate rejected-share/pool-luck observations from computation validity. |
| Stop and recovery | Operator remains present. Stop on system instability, manufacturer limit breach, unexpected warning or unacceptable responsiveness/noise/heat; restore known-good profile. Record CPU-specific limits before starting. Never change antivirus, Secure Boot, driver blocklists or custom MSR register arrays to make a test succeed. |
| Data/privacy | Configs/logs can contain wallet addresses, hostnames, usernames, paths and identifiers. Keep raw originals owner-controlled, prepare reviewed redacted publication copies, and never send them through website tools/analytics. No online benchmark submission without separate consent. |
| Uncertainty | State meter accuracy, sensor resolution, time alignment, ambient drift, shared-machine effects, run variability and configuration gaps. If a difference is within those limits, report inconclusive rather than improvement. No fabricated error bars. |

The durations/repetitions above are **proposed design choices**, not upstream requirements or performed tests. Pilot feasibility and meter resolution may require revising them before acquisition. A short safe feasibility run should establish the logging and stopping procedure before the full protocol is approved.

## Experiment specifications

Each experiment inherits the hardware/software/version, controls, repetition, limitations and privacy fields above; exceptions or extra requirements are explicit below.

| ID / research question | Required hardware and software / changed variable | Measurement method and controlled variables | Repetitions and additional limitations | Suitable visualization / publication and educational value |
| --- | --- | --- | --- | --- |
| E01 — How does selected worker count change sustained throughput and whole-PC efficiency on this PC? | One existing CPU PC and wall meter; pinned XMRig 6.26.0, reviewed CPU profile and telemetry logger. Change worker count only, preserving a documented affinity selection rule | Baseline automatic profile; select two or three lower-count alternatives appropriate to the CPU. Use common warm-up/window; record H/s, total wall W/kWh, allocations, temperatures and responsiveness. Keep algorithm, RAM, power limits and security/optimization state fixed | At least 3 launches per profile, balanced order, baseline repeat and second session. Topology/affinity changes can confound count; document exact workers. Do not force all logical processors or extrapolate another CPU | Worker-count line/table plus H/s-versus-wall-W scatter and run ranges. One sourced case-study page + redacted raw CSV/method. Explains why maximum occupancy and useful output differ |
| E02 — What is total active consumption, and what extra load is attributable to mining relative to a matched idle state? | Same PC/meter/software/version as E01; no CPU tuning. Measurement boundary fixed including display/peripherals | Three paired idle → active → idle cycles. Define idle as same signed-in state/background applications with mining stopped; wait for stabilization. Integrate energy over matched windows; report total active watts and idle watts separately, with incremental difference explicitly derived | At least 3 independent cycles and a second session if possible. Background jobs and sleep states matter; idle may not represent the owner's normal alternative use. Small deltas near meter uncertainty are inconclusive | Paired point/range chart and boundary diagram; measurement guide section with downloadable record. Shows why package power, total electricity bill and incremental attribution differ |
| E03 — What is the hashrate-versus-power trade-off among approved CPU operating profiles? | Same meter and pinned miner; two or three manufacturer-supported preset power profiles only, operator-recoverable; no voltage/clock recipe | Change only chosen power profile with identical worker/affinity/RAM allocation. Record actual sustained clocks, wall energy, thermals and H/s; calculate matched H/s/W | 3 launches/profile and repeat baseline. Presets may also affect fan/boost behavior; record combined effect rather than causal claim about watts alone. More risk/review than E01; defer until baseline stable | Pareto-style scatter with raw-run points/table, explain choice depends on owner's goal. A bounded follow-up, not overclocking instructions |
| E04 — How do reported Huge Pages allocations relate to measured performance under controlled conditions? | One compatible owner PC/meter; pinned miner; recorded existing privilege/OS policy. No policy/security weakening | Compare documented miner-level page setting only if safe and separately approved. Observe actual dataset/thread allocation, not merely requested setting; fixed workers/MSR/NUMA/load. Do not manufacture memory pressure or treat failed allocation as a randomized intervention | At least 3 valid runs/condition; allocation may not be controllable/repeatable. Reboot/order and memory layout confound results. Partial allocations observed opportunistically are observational cases, not proof of cause | Allocation/status table plus throughput/efficiency chart, methodological note in existing HP guide. No universal “up to” performance headline |
| E05 — Does a short benchmark predict sustained throughput in this configuration? | Same PC/meter; XMRig 6.26.0 fixed-work offline benchmark and separately approved sustained workload; record mode and work size | Pair short benchmark and sustained window at same settings, recording initialization separately. Calculate comparable active H/s and time course; distinguish fixed work from job/donation/pool activity | 3 pairs, balanced order and cooldown. Finite benchmark duration varies by CPU; initialization/gaps and network effects prevent claiming perfect equivalence | Paired run plot + time series, benchmark-literacy guide linked from LOW. Teaches why database maxima are conditional |
| E06 — How do temperature, clocks, wall power and throughput evolve during a bounded session? | PC/meter plus manufacturer-supported telemetry; pinned miner/version; ambient thermometer if available | One fixed profile for up to 60 minutes after safe feasibility, 10-second logging where feasible. Align room temperature, clock, CPU temperature, H/s and wall energy; record fan policy. Operator may end earlier | 3 independent sessions with cooldown and same conditions. Sensor placement, logging overhead and fan response confound cause; no claim temperature alone explains rate | Aligned small-multiple time series with warm-up shaded and accessible summary table. Illustrates sustained load/stability, no universal safe-temperature threshold |
| E07 — Does ordinary concurrent PC activity alter mining efficiency and usability? | Same PC/meter/pinned software; predefined owner-approved light workload, no private content recording | Alternate mining-only and one fixed reproducible workload; same worker profile/power plan and matched windows. Record background task version and workload duration; optional operator notes clearly qualitative | 3 paired launches/condition, balanced order. Workload may be hard to reproduce; subjective responsiveness is not a benchmark score. Defer until E01/E02 support reliable measurements | Paired chart/table and short limitations note. Helps explain active-use versus idle mining without advising hidden/background mining |

## Measurements, derived values and estimates

- **Measured:** meter interval energy/elapsed time, directly recorded total hashes/rate windows, reported allocation and sensor observations. Sensor readings have uncertainty and are not independent lab calibration.
- **Derived from measurements:** average wall watts, matched H/s per W, incremental active-minus-idle watts. Retain units, intervals and uncertainty.
- **Scenario estimates:** extending observed W over chosen hours/days or applying an entered tariff/network/price assumption. Show assumptions/date and keep separate from actual metered energy, rewards or money received.
- **Not established:** universal hardware performance, expected ROI, long-term hardware wear, mining reward guarantees, carbon footprint or a product performance comparison.

If measuring actual pool sessions later, received XMR and accepted shares are different variables; windows, pool policy and luck need their own design. Do not use the existing profitability calculator to validate actual payouts or describe it as a pool simulator. No MSR-on/off study is prioritized because security-sensitive comparability and unsupported changes can outweigh the value.

## Publication and reproducibility plan

Before the future experiment, write and date the protocol, allowed settings, failure criteria, operator consent, data-retention/redaction policy and hardware limits. Version any protocol amendment. Do not invent a dataset template populated with plausible results.

After a run, release only reviewed material: concise question/answer, exact setup/version/algorithm, method, run table, traceable units, chart with table/text alternative, exclusions and inconclusive observations, limitations and correction contact. Offer redacted raw CSV and a schema/data dictionary if the owner approves. Include hashes of reviewed config/log artifacts where useful without exposing secrets or identities. Owner should choose an explicit license for original data/figures and confirm permission for any third-party screenshots before release; software licensing does not settle those rights.

Use one research case study attached to existing Learn/Guides links initially. Preserve graphite/orange chart identity and accessible labels, static SVG/table output and reduced-motion support. Do not create a Research navigation section until multiple completed studies need it. E01's thread chart can support THREADS/LOW; E02's boundary diagram belongs next to ELECTRIC measurement help. Do not repeat complete methods/data in every article: link at the exact measurement claim.

Potential citation value comes from transparent conditions, complete runs and reusable methods, including null findings. No external outreach, repository submission or backlink solicitation is authorized here. Future community sharing must follow [verified channel rules](m13b-promotion-opportunities.md).

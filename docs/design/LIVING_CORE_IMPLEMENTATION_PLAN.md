# Living Core D02 implementation plan

D01 defines the visual and truth contract in [Living Core design](LIVING_CORE_DESIGN.md). D02 is a frontend-only, reviewable prototype. Keep Mining controls, Rust/Tauri commands, telemetry/event contracts, wallet/pool setup and `website/` untouched. Approved static assets are a prerequisite; keep the existing `EmberCore` visible until they exist.

1. **Approve art and layout.** Review the 320 × 180 transparent still, individual anchored layers, and `scene-fallback.png` against the D01 asset checklist. Place versioned assets in `public/living-core/v1/` only after approval. Record dimensions and pose names in a small manifest next to assets. Inspect native Overview screenshots at 1440, 1200, 1024 and 820 px, plus 200% zoom, before locking the scene slot.
2. **Add a pure state adapter.** Create `src/livingCoreState.mjs` with `src/livingCoreState.d.mts` (or a TypeScript module if tests can import it without a new runner). Input: current `MiningSessionStatus | null`, `sessionStatusUnavailable`, and readiness/status fallback already available in `App.tsx`. Output: a discriminated visual pose and freshness qualifier, plus a short text status supplied outside the illustration. Precedence: failed status request/unknown → unavailable; startup stage → starting; Rust lifecycle otherwise; stale/unavailable telemetry suppresses mining activity without changing lifecycle. Preserve `stopping`, `paused`, `stopped`, `notConfigured` and `error` distinctions. No data fetching or control calls in this module.
3. **Build isolated static scene.** Add `src/components/LivingCore.tsx` and scoped styles (for example `src/components/LivingCore.css`). Use layered `<img>` elements, `image-rendering: pixelated`, explicit logical dimensions, integer scale/crop rules, and a restrained CSS ambient halo. Mark decorative layers `aria-hidden`; retain the Overview headline and status copy as the accessible source. On missing art, show the existing `EmberCore` rather than an invented mascot. Do not replace the Mining `EmberCore`.
4. **Preview without mining.** Add a development-only local preview route/component or Storybook-free fixture using hard-coded adapter inputs, isolated from production navigation and Tauri commands. Show every lifecycle pose, stale/unavailable qualifiers, and reduced-motion/static mode. Do not simulate shares, blocks or earnings. Keep the preview out of the production build surface if it exposes controls or test states.
5. **Integrate Overview only.** Replace the decorative `<EmberCore>` in `App.tsx` `.hero-core-wrap` with `LivingCore` after asset approval, passing adapter output. Preserve current headline, navigation action and `OverviewMiningTelemetry`. Adjust only the relevant Overview layout CSS at actual window widths; leave the Mining screen untouched.
6. **Add motion only for approved sheets.** If frames are approved in D02, put a frame stepper in a small hook owned by the scene. Start it only while mounted, visible and motion allowed; advance at the authored 4–8 fps, reset on pose change, and clear timers/listeners on unmount. Use a static frame for reduced motion, document hidden windows and image-load failures, and avoid a continuous 60 fps redraw loop. Event reactions remain out of D02 unless a reliable session boundary is already present and separately approved.
7. **Verify.** Unit-test the pure adapter's precedence (especially cached mining plus failed poll, stopping versus starting, paused, and stale/mining). Test static markup and reduced-motion behavior without mirroring CSS implementation. Run `npm run build` and focused frontend tests; investigate any existing Vite SSR `EPERM` failure separately. Inspect native Windows WebView2 at target widths, 200% zoom, high DPI and reduced motion. Confirm no clipped status text, blurry sprite edges, animation while hidden, CPU churn at idle, false success cues or changed mining controls. Record owner visual acceptance before expanding to Mining or adding event reactions.

The first deliverable is a static, approved Overview illustration with truthful state selection and a safe fallback. Motion is a later, independently verifiable increment within D02 if the approved frame assets are ready.

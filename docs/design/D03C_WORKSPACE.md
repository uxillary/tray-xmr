# D03C unified workspace

## Before implementation

- **Current journey:** Overview shows a large world and duplicated telemetry, Mining owns setup, Start/Stop and an eight-row reverse-ordered Stream; Activity is an empty history placeholder. Settings contains setup links and opt-in diagnostics. Navigation is component state, with no existing URL router/deep-link contract.
- **Sources:** App serially polls Rust `mining_status` (1s), readiness on navigation/terminal states, `mining_events` (1.2s, formerly Mining only), and system observations (5s). Start/Stop, setup validation, consent and contribution remain Rust-owned. Events are a 256-entry process-local buffer, not saved history; payloads omit pool endpoints.
- **Animation:** `livingCoreState` separates lifecycle/freshness; `createFramePlayer` schedules one cancellable low-rate timeout. v2 uses 320×180 layered PNG cells with an approximately 80px stationary character, enlarged to 2×. Visibility, intersection, reduced motion and asset failures already have fallbacks.
- **Constraints:** independently scrolling sidebar/workspace, narrow 820px windows and 200% zoom. Existing large scene stacks above controls/data and crowds short windows.
- **Reuse:** MiningSetup command handlers, all four setup forms/disclosures, telemetry formatting/provenance, diagnostics, lifecycle adapter, scheduler and event presenter. Retire production Overview/Activity compositions; recompose telemetry and Stream rather than duplicate mining state.

## Proposed composition and constraints

- **IA:** Home (setup → session → recovery, always-available activity); Settings (configuration links and advanced diagnostics). Legacy `/overview`, `/mining`, `/activity` and equivalent hash destinations resolve to Home. `/settings` resolves to Settings.
- **Desktop:** compact lifecycle/action strip; 320×144 logical workshop at integer 1× or 2× beside a large rate; compact pool/power/time/results rail; generous recessed chronological activity viewport; technical details and saved setup below disclosures. Setup appears in Home before activity when needed.
- **Narrow:** status/44px+ action first, workshop and rate stack only as needed, two-column then single-column facts, activity wraps technical details without horizontal scrolling. Navigation becomes a compact top row under zoom pressure.
- **Character:** target 32px logical height, simplified bespoke small sprite preserving reference identity. Workshop path bounded between x=78 and x=200, resting mat at x=78 and compact crystal/pedestal near x=230; fixed ground line. No game engine, continuous render loop or event celebrations.
- **Behaviour:** deterministic 4fps ambient controller. Ready rests/blinks/short wander; Starting approaches crystal; confirmed fresh positive Mining approaches/tends/steps back/returns; Stopping withdraws then returns to rest; Stopped settles; Error faces machinery; stale/unavailable suppress active work. Rapid changes retarget from current bounded position. Hidden/reduced-motion scenes have no animation timeout; static poses communicate no extra facts.
- **Asset production:** attempt a dedicated small sprite with built-in imagegen, evaluate against reference at actual size, retain versioned approved source material. Generated sprite fidelity and native rendering require owner review; no claim of final artwork or owner acceptance.

## Delivered implementation

Home replaces the large Overview hero, separate Mining page and empty Activity destination. `App.tsx` keeps one Rust session/readiness/event source. `MiningSetup` remains the sole Start/Stop/setup command owner and stays mounted across navigation. During an owned active session Settings shows the same status/Stop strip through its controls-only presentation; it does not mount another handler or animate a hidden workshop. It composes a sticky lifecycle/action strip, compact world/rate, operational facts, technical Details, contextual setup/recovery and a full activity viewport. Setup displays one of Wallet, Pool, Power and Review at a time, automatically advances after successful saves and keeps the original consent/security/contribution disclosures. Saved setup is closed under Manage setup; Settings links open it explicitly. Device observation previously on Overview remains accessible under Settings → Device information. No Insights placeholder was added.

The scene is **320×144 at integer 1×**, with a dedicated **32×32** character sheet (four distinct poses). This deliberately supersedes the initial optional 2× layout proposal: actual inspection showed that a larger world displaced activity. A resting rug, continuous path, amber crystal, compact pedestal, flywheel and pipes establish a miniature workshop. v1/v2 and all owner references are retained. Runtime v3 assets are in `public/living-core/v3/`; source plates are in `docs/design/d03c-sources/`. `scripts/prepare-workshop.py` reproducibly normalizes the generated source cells, shares the palette/baseline and validates dimensions, binary alpha, distinct poses and manifests.

`workshopBehaviour.mjs` owns deterministic bounded ambient movement at 4fps (x70–204, rest x78, work x200, ground y118). Ready rests and occasionally wanders 16px; Starting approaches; fresh positive Mining tends, withdraws 16px to inspect and returns. Stopping allows a final gesture then returns. If Rust reaches Stopped quickly, the bounded return finishes before the timer ends. Attention/unconfirmed data freezes work with a concerned pose. Stopped settles, paused rests. Rapid changes retarget from the existing position. Hidden/offscreen/reduced-motion scenes suspend scheduling and use composed static poses. No result reactions or per-hash timing exist. One timeout maximum; no canvas/game engine/continuous rendering.

The Stream renders the supplied buffer in **backend chronological order, oldest → latest**, rather than the old eight-row newest-first presentation. At most 256 rows render. Timestamps, event/source marker, icon, friendly wording and explicit severity are separated. Each row exposes the supplied source/category/kind/context/ID in Technical detail; Verbose opens that information across rows. Endpoints are not invented because event payloads omit them. Ordinary telemetry cannot emit rows. While following, new rows remain visible; reading older rows preserves scroll and exposes a new-event count/Return to latest. Poll failures retain received rows with an explicit warning. An empty buffer deliberately shows a calm empty state. The footer states that the buffer covers this app run only.

The hierarchy is everyday status/world/rate/facts/activity → Details and Manage setup → Settings diagnostics/device observations. Long operational explanations moved into disclosures; current state and action are no longer repeated in competing heroes. Existing contribution slot remains visible, with its complete accounting and separate XMRig donation under Details. No Rust, backend DTO, validation, consent contract, Start/Stop semantics, contribution implementation, licensing or `website/` files changed.

## Limitations and owner acceptance

The generated small sprite preserves the reference's silhouette/eyes/tuft, but it is a **four-pose interim animation set awaiting owner art review**. It is simplified independently, not the old 80px sprite shrunk by CSS. There is no separately authored blink/rest/sit or complete directional walking cycle; walking alternates the neutral/step poses and mirrors direction, and tending alternates neutral/reach. Further hand-authored frames could improve feet and hand articulation. The generated plates did not honor exact export dimensions; the reproducible build normalizes their cells onto the runtime pixel grid. These are coherent implementation assets, not a claim of final approved artwork.

Actual browser/WebView **200% zoom could not be confirmed** through native zoom shortcuts; the 410px equivalent of an 820px window was inspected and corrected, but is not reported as actual 200% acceptance. Packaged high DPI, CPU/GPU profiling, Windows High Contrast and full screen-reader acceptance remain manual checks. The feed does not promise persistent history. No event/share celebrations, new telemetry history, profitability or earnings were added.

Owner steps:

4. Explicitly accept or request revisions to composition, sprite identity/scale, motion and Stream hierarchy. Owner approval, packaged performance and the outstanding native accessibility/zoom checks remain separate from the implementation/test pass.

## Built-in imagegen prompt set

Both plates used built-in imagegen; no CLI/API fallback. The character reference and prior v2 still were supplied as identity/style references, not copied as the miniature sprite. Runtime normalization and crystal/pedestal reuse are recorded above.

**Character (transparent):** Use case: identity-preserve. Asset type: production pixel-art character sprite sheet for Ember desktop app, dedicated simplified SMALL 32x32 logical-pixel character. The first reference image is the canonical identity; second is prior oversized version, do not copy its large size. Create a transparent PNG sheet, exactly 1024x256 pixels, with FOUR equal 256x256 cells in ONE horizontal row. Each cell contains ONE small pixel-art Ember the Squish, same scale, same baseline, centered with generous transparent margins. Each cell is a 32x32 logical pixel grid enlarged precisely 8x nearest-neighbor, all edges aligned to 8px blocks, no antialiasing. Simplify intentionally for 16-bit RPG readability: round orange/yellow body, two oversized dark expressive eyes with white highlights, tiny orange arms and feet, distinctive curling flame tuft. NO helmet/tools/clothes. Four poses left to right: 1 relaxed neutral looking slightly right, 2 walking right with one tiny foot extended, 3 tending right with right arm out, 4 concerned looking right with worried eyebrows. Keep body, eyes, tuft, palette consistent, no environmental art, no text, no separators, no shadows outside character, no spark particles. Character fills about 26 pixels wide and 30 pixels high of each logical cell. True transparent background, no checkerboard. Preserve innocent slightly clumsy charm. Must be tiny readable sprite art rather than detailed illustration.

**Workshop (opaque):** Use case: stylized-concept. Asset type: background plate for tiny 16-bit RPG workshop inside a premium dark desktop app. A wide miniature interior, 320x144 logical pixels displayed enlarged nearest neighbor, exact crisp pixel-art, limited warm graphite/brown/amber palette. Quiet cozy workroom, shallow RPG front/three-quarter perspective. Back wall in upper 70 pixels: a low shelf of tiny tools and one amber lamp to left, a modest brass flywheel and three small pipe details to far right, empty quiet wall in center. Continuous flat walkable wooden floor in bottom 60 pixels. A tiny dark rust-orange rectangular resting rug at logical x60..100 y107..118. Clear open path along y115 between x78 and x204. Empty space at x230 y106 to place a separate 28px tall amber crystal and compact pedestal. NO character, NO crystal, NO pedestal in this plate. Restrained light only, charming sparse handcrafted pixels rather than cavern, no dramatic spotlight. Important: open floor must read as a place for a 32px tall RPG creature to walk. Subtle dark edges, no border, no UI, no text, no coins or mining helmets, no glow particles. Landscape 20:9 composition. No smooth painted illustration; hard pixel steps only.
